## 图 1:整体架构(开场用,约 60 秒)

> "这是我用 Python 写的终端 AI 编程助手,类似一个自研的 Claude Code。
> 主链路是:用户在终端输入自然语言,CLI 读取 Profile 配置、组装出运行时;
> 核心是一个执行循环——把上下文发给大模型,模型决定调用什么工具,
> 工具去工作区读写文件、跑测试,结果再喂回模型,如此反复,直到模型给出最终回答。
> Coding 模式的最终回答会经过完成证据门:有代码净修改时检查验证证据,无修改或只有文档修改时可以直接放行。
> 数据分三处落:会话记录用 JSONL 只追加不回改;MEMORY.md 是跨会话的长期记忆;
> 工作区文件是唯一被真实修改的代码。
> 上下文管理负责 token 预算,还会用 BM25 自动从旧会话召回相关历史。
> 整个 Engine 内核不认识具体模式,换一套 Profile 就能变成只读的 review 或纯聊天模式。"

**设计意图(如果被问"为什么这么分层")**:Engine 与 Profile 分离,内核不知道 Coding/Review/Companion 的存在,能力组合由 Profile 决定——这样加新角色不用改内核。

## 图 2:完成证据门(深入讲,约 90 秒,这是你的王牌)

> "这个项目里我最想展开的是完成证据门,它解决一个大模型的老毛病:
> **模型爱说'我做完了',但可能根本没验证过**。
>
> 我的方案是不信声明、只认证据。模型输出一段不带工具调用的文字时,
> 有未验证修改或待验证候选时,文字先缓冲;其他情况可以正常流式展示。完成门会检查:
>
> **第一,文件净变化。** 任何写文件的工具第一次碰某个路径之前,我会先记录基线快照,
> 也就是文件是否存在加内容的 SHA-256 指纹。宣布完成时重新读一遍做对比——
> 所以临时文件建了又删、改了又改回原样,都骗不过它,因为这些不算'净变化'。
>
> **第二,新鲜验证。** 最后一次修改之后,必须有一次跑测试或 lint/build 类命令成功,
> 退出码为 0。顺序很关键:先测试后改代码,证据就是过期的,必须重来。
>
> 有代码净变化时才要求新鲜验证。如果已有待验证候选且版本没变,就复用它并附上验证标记;无净变化或只有文档变化则直接放行。
> 如果证据不足,就退回去验证:插一条内部提醒让模型去跑测试,继续循环。
> 如果模型始终拿不出证据,比如连续两次都缺失,就走兜底:
> 把有效候选回答交付,并贴上'未验证'标记。这个门检查验证是否执行成功,不能证明整个需求都正确实现。"

## 高频追问 Q&A(面试官大概率会问)

**Q1:为什么用 SHA-256,不用修改时间戳?**
> 时间戳不可靠(工具可能不改内容也 touch 文件,或者精度不够)。SHA-256 对内容敏感,改一个字节指纹就变;而且临时文件建了又删,存在性对比直接判无变化。

**Q2:'新鲜验证'为什么要绑定'最后一次修改之后'?**
> 这是证据的时序有效性问题。测试通过只说明对应检查在当时成功,不代表没有其他问题。如果之后又改了代码,就需要重新验证。我用单调递增的修改版本号,验证发生时记录当时的版本,再和有净变化路径的最后修改版本比较。

**Q3:验证提醒(nudge)会不会污染会话历史?**
> 内部验证提醒和被拒绝的候选不写入 JSONL,只有最终交付的回答会作为正式 assistant 消息保存。

**Q4:如果一直验证不通过,会不会死循环?**
> 有连续缺证据的拒绝次数限制,也有整个循环的 max_turns 上限。耗尽轮数时,只有仍与当前修改版本一致的候选才会带'未验证'标记交付,不会把过期答案当成当前结果。

**Q5:这个门为什么放在 Coding Profile 里,不放进 Engine 内核?**
> 因为'什么算修改、什么算验证'是 Coding 专属策略——write_file、pytest 这些名字只在 Coding 世界存在。Engine 只消费一个 evaluate() 接口,换个 Profile 可以有完全不同的完成策略。这是关注点分离。

**Q6:BM25 召回旧会话,语料很少怎么办?**
> BM25 的 IDF 在极小语料下会退化成 0,这时自动降级为关键词覆盖匹配兜底,避免'明明有却搜不到'。

**Q7:token 预算怎么估?**
> 已知模型走 tiktoken 官方映射,未知模型明确标记为通用回退;估算包含消息元数据和工具定义开销。服务端 usage 与本地估算分开展示。只有 HTTP 400/413 且响应体命中上下文超限标识时,才强制压缩后重试一次。

## 一句话总结(背下来,开场或收尾用)

> "我把模型声明和执行证据分开:通过文件指纹判断是否有净修改,再检查修改后的验证结果;缺少证据时如实标注,不把测试成功夸大成需求全部完成。"

## 维护方式

- 图的源数据是同目录的 `.workflow.json` / `.architecture.json`,代码更新后改 JSON 再重新生成就行,不用从头画。
- 重新生成命令(在技能目录下):
  `node bin/archify.mjs deliver workflow <json> <html> --quality showcase`
- JSON 里每个状态/连接都对应真实代码:`completion_gate.py`(完成门)、`machine_loop.py`(循环)、`docs/architecture.md`(分层)。
