# v2 开发计划

[v2 架构](architecture.md) · [行为契约](behavior-contracts.md) · [术语表](../CONTEXT.md)

这份计划把 v2 拆成 15 个阶段：先做出一个最小的、能跑起来的 Agent，之后每个阶段只把一个模块做深一层。每个阶段结束时，测试全部通过，并且能端到端运行一次任务。

v1 的代码保存在 Git 标签 `v1-final`。v2 直接写在 `src/auto_coding_machine/`，开工时删除 v1 的代码和测试，再按行为契约逐条重写。

## 推进路线

```mermaid
flowchart LR
    A["0 准备"] --> B["1 最小链路"] --> C["2 权限与审批"] --> D["3 会话记录"] --> E["4 事件"]
    E --> F["5 模型网关"] --> G["6 上下文"] --> H["7 记忆"] --> I["8 MCP"]
    I --> J["9 Coding 应用"] --> K["10 Docker 沙箱"] --> L["11 LSP"] --> M["12 只读子代理"]
    M --> N["13 界面与插话"] --> O["14 ACP 协议"]
```

| 部分 | 阶段 | 目的 |
| --- | --- | --- |
| 一、骨架 | 0–4 | 让 Agent 能循环工作，再依次加上审批、持久化和对外通知 |
| 二、接入真实世界 | 5–8 | 真实模型、长对话、长期记忆、外部工具 |
| 三、Coding 应用 | 9–12 | 编码助手本身，加上隔离、代码理解和分工 |
| 四、使用方式 | 13–14 | 终端界面和编辑器 |

## 每个阶段的写法

每个阶段都按同样的五项描述：

- **涉及模块**：这一阶段新建或加深的模块。
- **要做什么**：具体工作。
- **完成效果**：做完之后，使用者能感受到的变化。
- **边界**：这一阶段明确不做的事。
- **验收**：要通过的契约编号（见[行为契约](behavior-contracts.md)），以及一项端到端检查。

## 每个阶段都遵守的做法

1. **先写测试，再写代码。**按验收里的契约编号写测试，确认测试会失败，再写刚好让它通过的实现。
2. **测试只走公共接口。**测试替身只用在外部边界：脚本化模型、内存会话存储、本地 HTTP 服务、本地 MCP 或 ACP 测试程序。需要 Docker 或语言服务器的测试，在环境缺失时明确跳过，并写明原因。
3. **阶段结束的标准。**`uv run pytest -q` 全部通过，依赖方向检查（`import-linter`）通过，端到端检查通过。
4. **提交要小。**调整结构的改动和改变行为的改动分开提交。

## 第一部分：骨架

### 阶段 0：准备

**涉及模块**：全部模块的空包，依赖方向检查

**要做什么**
- 删除 v1 的代码和测试，按架构文档建立空的包结构。
- 用 `import-linter` 把"依赖只能沿箭头方向"写成自动检查。
- README 的状态改为"开发中"。

**完成效果**
仓库里只剩 v2 的骨架；只要有人写出反方向的导入，依赖检查就会立刻失败。

**边界**
- 不写任何功能代码。

**验收**
- 契约：无。
- 端到端检查：`uv run pytest -q` 和 `lint-imports` 都能运行并通过。

### 阶段 1：最小链路

**涉及模块**：`contracts`、`tools`、`core`

**要做什么**
- `contracts`：`AgentResponse`、`ToolCall`、`ToolResult` 等数据类型。
- `tools`：注册工具，按名称执行。
- `core`：调用模型、执行工具、把结果交回模型，直到模型给出最终回答；内存中的会话；组装入口 `open_session`。

**完成效果**
用一个脚本化的假模型加一个工具，就能完成一次完整任务。这是 v2 第一次能跑起来。

**边界**
- 没有权限审批，所有工具都直接执行。
- 不写文件记录，不做上下文压缩，不接真实模型。

**验收**
- 契约：C1.1、C1.2、C1.4、C1.8、C1.12、C2.9、C10.1。
- 端到端检查：脚本化模型调用一个工具后给出回答，结果为 `success`。

### 阶段 2：权限与审批

**涉及模块**：`policy`、`core`

**要做什么**
- `policy` 规则引擎：规则按优先级匹配，给出允许、询问或拒绝；支持计划模式、无人值守模式、按参数判断、路径规则；规则出错时按拒绝处理。
- `ToolBatch`：一次回复里的多个工具调用按顺序处理，遇到需要询问的调用就暂停。
- 任务对象：`start()`、`resolve_permission()`、`cancel()`，以及五种运行结果。

**完成效果**
危险操作会停下来等你批准；你拒绝某一步，其他步骤照常进行；随时可以取消，没有执行的步骤会留下"未执行"回执。

**边界**
- Coding 专属的权限配置（默认权限表、保护路径）放到阶段 9，这里只在测试中使用示例规则。

**验收**
- 契约：C1.3、C1.5、C1.6、C1.7、C2.1–C2.6、C2.8、C2.10、C2.11、C2.13–C2.15。
- 端到端检查：一个需要询问的工具让任务暂停，批准后任务完成；另一次取消后得到 `cancelled`。

### 阶段 3：会话记录

**涉及模块**：`session`

**要做什么**
- JSONL 会话记录：只追加；包含 `user`、`assistant`、`tool` 三种记录类型；读取时跳过损坏行。
- 恢复会话（新建、最近一次、指定 id），校验会话 id，提供会话列表。
- 修复中断留下的工具调用；写入失败时立刻以 `session_write_failed` 结束任务；支持自定义存储。

**完成效果**
关掉程序再打开，对话还在；程序在工具执行到一半时中断，重新打开后能看出哪一步状态不明。

**边界**
- 不做压缩，`compaction` 记录放到阶段 6。

**验收**
- 契约：C3.1–C3.10、C3.12–C3.14、C3.16、C3.17。
- 端到端检查：完成一次任务后关闭程序，用同一个会话 id 重新打开，历史完整。

### 阶段 4：事件

**涉及模块**：`core`

**要做什么**
- 单一的事件订阅方式；对外提供脱敏后的宿主可见视图；观察方出错不影响任务。
- 状态栏：根据事件统计工具调用，每次请求时临时附加 `<agent_status>`。
- 诊断记录：可选的观察方，把每次模型请求和回复写进单独的文件。

**完成效果**
外部程序能完整看到任务进展，但拿不到原始参数和密钥；排查问题时可以打开诊断记录逐条查看。

**边界**
- 不做界面，事件只给程序使用。

**验收**
- 契约：C4.17、C5.1–C5.11。
- 端到端检查：注册一个观察方，打印一次带审批任务的完整事件序列，最后一个事件是结束事件。

## 第二部分：接入真实世界

### 阶段 5：模型网关

**涉及模块**：`model`

**要做什么**
- 支持 OpenAI 兼容和 Anthropic 两种接口，结果统一转换成 `AgentResponse`。
- 流式输出、用量与费用统计、上下文超限识别、`tool_choice` 规则。
- 还没收到任何回复时，对限流、服务端错误和连接错误做有限次数的退避重试；主模型不可用时切换到备用模型。

**完成效果**
示例程序第一次接上真实模型跑通；临时的网络抖动不再直接导致任务失败；能看到每个模型用了多少 Token、花了多少钱。

**边界**
- 已经开始接收回复后出错不重试，上下文超限也不重试。
- 不做界面上的流式展示。

**验收**
- 契约：C10.2–C10.5、C10.7、C10.8、C11.1–C11.6。
- 端到端检查：`examples/order_assistant.py` 用真实模型完成一次带审批的任务。

### 阶段 6：上下文

**涉及模块**：`session`、`core`

**要做什么**
- Token 计数与预算：窗口来源的优先级，为输出预留空间。
- 压缩：请求摘要；摘要失败时改用确定性摘录；冷却期；不拆开工具调用和它的回执。结果写成 `compaction` 记录。
- 上下文超限时强制压缩，只重试一次。
- 历史召回，以及请求组装顺序。

**完成效果**
长对话不会因为超出窗口而中断；重启之后从最近一次压缩继续，不用加载全部历史；以前会话里的相关内容会自动召回。

**边界**
- 不做外部记忆召回，放到阶段 7。

**验收**
- 契约：C1.9–C1.11、C3.11、C3.15、C4.1–C4.16。
- 端到端检查：用很小的预算跑一段长对话，触发压缩后关闭并恢复会话，视图从摘要开始。

### 阶段 7：记忆

**涉及模块**：`memory`、`core`

**要做什么**
- 本地 Markdown 记忆：容量上限、写入加锁、原子替换。
- 外部记忆接口：召回与写回，带用户和团队作用域；腾讯记忆服务 Adapter。
- 任务成功后才写回；超时标记为"结果未知"，不重试。

**完成效果**
Agent 能记住你的偏好，跨会话保留；接入外部记忆服务后，不同用户和团队之间的记忆互不可见。

**边界**
- 写回默认关闭，只有调用方显式提供写入器时才启用。

**验收**
- 契约：C6.1–C6.16。
- 端到端检查：一次会话中写入一条记忆，新会话的请求里能看到它。

### 阶段 8：MCP 客户端

**涉及模块**：`mcp`

**要做什么**
- 连接 stdio 和 HTTP 两种 MCP 服务器，把它们的工具注册进工具集合。
- MCP 工具默认需要询问，服务器故障时隔离处理。

**完成效果**
不用写 Python，只要在配置里加一个 MCP 服务器，就能给 Agent 增加新工具。

**边界**
- 只做客户端，不把我们自己的工具作为 MCP 服务提供出去。

**验收**
- 契约：C12.1–C12.4。
- 端到端检查：连接一个本地 MCP 测试服务器，Agent 调用它的工具并完成任务。

## 第三部分：Coding 应用

### 阶段 9：Coding 应用

**涉及模块**：`environment`（本机实现）、`coding`

**要做什么**
- `environment` 的本机实现：文件操作和命令执行都经过它。
- 工作区路径限制、12 个代码工具、完成验证、Coding 提示词、Coding 默认权限与保护路径。
- 三套内置 Profile 和 YAML 校验。
- 文件检查点与回退。

**完成效果**
不用界面，也能在自己的程序里调用一个完整的编码助手：读代码、改文件、跑测试、验证修改；改坏了可以恢复到某次任务之前。

**边界**
- 命令只在本机执行，Docker 放到阶段 10。
- 检查点不覆盖 Shell 命令造成的修改。

**验收**
- 契约：C2.7、C2.12、C7.1–C7.13、C8.1–C8.10、C9.1–C9.14、C13.1–C13.4。
- 端到端检查：在临时项目里完成一次"修改代码并跑测试"的任务，再恢复到任务之前的状态。

### 阶段 10：Docker 沙箱

**涉及模块**：`environment`（Docker 实现）

**要做什么**
- `environment` 的 Docker 实现：只挂载工作区，默认关闭网络。
- 由 Profile 选择使用本机还是 Docker 执行环境。

**完成效果**
Agent 执行命令时碰不到工作区以外的文件，也连不上网络，可以放心开启无人值守模式。

**边界**
- 不做远程执行。
- Docker 不可用时在任务开始前报错，不会改用本机执行。

**验收**
- 契约：C15.1–C15.3。
- 端到端检查：阶段 9 的同一个任务改在 Docker 中运行，结果一致。

### 阶段 11：LSP 集成

**涉及模块**：`coding`

**要做什么**
- 用 `multilspy` 启动语言服务器，提供诊断、跳转定义、查找引用三个只读工具。
- 编辑文件后可以附带诊断结果。

**完成效果**
Agent 改完代码，马上就能知道有没有引入类型错误；理解陌生代码时，可以直接跳转到定义。

**边界**
- 只读，不做重命名这类写操作。

**验收**
- 契约：C17.1–C17.3。
- 端到端检查：对一个带类型错误的样例项目取得诊断，并跳转到某个函数的定义。

### 阶段 12：只读子代理

**涉及模块**：`core`

**要做什么**
- 新增 `task` 工具：在独立的上下文中运行一个只读 Profile，只把最终结论交回主任务。

**完成效果**
大范围的调查和搜索交给子代理去做，主对话的上下文保持干净，不会被大量文件内容塞满。

**边界**
- 子代理只有只读工具，不触发审批，也不能再创建子代理。
- 不做可写子代理或多代理协作。

**验收**
- 契约：C14.1–C14.4。
- 端到端检查：主任务让子代理调查一个问题，拿到结论后继续完成任务。

## 第四部分：使用方式

### 阶段 13：终端界面与运行中插话

**涉及模块**：`tui`、`core`

**要做什么**
- Textual 界面、斜杠命令（包括回退命令）、流式展示控制。
- 执行核心支持运行中插话，界面在任务运行时也允许输入。
- README 补回使用说明。

**完成效果**
`python -m auto_coding_machine` 重新可用，覆盖 v1 的全部功能；任务进行中可以随时补一句话调整方向，不用取消重来。

**边界**
- 界面只通过事件和命令与核心交互，不直接读写会话文件，也不直接执行工具。

**验收**
- 契约：C10.6、C16.1–C16.3。
- 端到端检查：在终端里完成一次带审批的任务，中途插一句话，并在下一轮请求中生效。

### 阶段 14：ACP 协议

**涉及模块**：`acp`

**要做什么**
- 用官方 `agent-client-protocol` SDK 提供 stdio 服务端：事件转为通知，审批转为客户端请求。
- 同步的核心在后台线程运行。

**完成效果**
Zed、JetBrains 等支持 ACP 的编辑器，可以直接把这个 Agent 当作内置助手使用。

**边界**
- 只做 stdio 传输，不做 HTTP 和 WebSocket。

**验收**
- 契约：C18.1–C18.3。
- 端到端检查：用本地 ACP 客户端完成一次带审批的任务。

## 明确不做的事

- **用户可配置的 Hook。**拦截操作用权限规则，操作后的处理用事件观察，这两样已经覆盖了它的主要用途。
- **可写子代理与多代理协作。**
- **会话分支、异步公共接口、插件市场。**
- **从 YAML 动态导入任意 Python 代码。**
