# 通用 Profile：一份可以自由搭配的预设

状态：待实施。本文是需求与设计方向，字段和接口尚未落地。

[规划入口](README.md) · [当前配置指南](../profiles.md) · [运行时边界](2026-09-05-runtime-boundaries.md)

## 想解决什么

把 Profile 理解成游戏的播放集：选一套预设，就装配它的提示词、工具、Skills 和模型。编程、审查、陪伴是预设示例，不应成为只能由程序员扩展的固定类型。

当前 `kind` 同时决定默认值、工具范围、修改验证和 Plan 模式可用性。比如陪伴配置不能选择读文件工具。下一版要拆开这些绑定，用户编辑配置就能组合已有能力。

## 第一版范围

- 内置与自定义配置使用同一结构、校验和组装流程；内置预设保留现有默认体验。
- 显式选择提示词、工具、Skills、模型、输入预算、项目指令加载和修改验证策略。`verify_changes` 是候选字段，尚不能写入当前 YAML。
- 工具从已有注册表选择；未知名称报错。配置选择能力，执行层仍检查权限；不能靠提示词、Skill 或关闭完成验证绕过权限。
- `examples/profiles/` 只放示例；`profile_configs/` 放用户启用的配置。支持按自定义 name 或路径加载，列表和命令使用同一解析规则。
- name 决定同一工作区中的状态范围。不同 name 隔离会话、输入历史和记忆；两个配置同名不能被默默合并或遮盖，应明确报错并指向冲突文件。
- 配置仅在启动或输入空闲时切换；先验证新配置成功，再结束旧运行时。运行中的工具不被中途换配置。

Skills 是说明文档，不是新工具的安装器。没有可用技能时隐藏搜索和加载入口的行为继续保留。

## 如何兼容旧配置

1. 保留 `coding`、`review`、`companion` 名称和已有状态目录。
2. 旧 `kind` 作为兼容输入，转换为明确的默认能力与策略，再走统一校验；新配置不依赖 kind。旧 review / companion 不因升级自动获得额外工具。
3. Plan 是否可用按实际能力和执行策略判断；保留只读约束，不能继续依赖 `kind == coding`。
4. 保持默认 Coding 的旧记忆路径兼容，单独记录这项历史例外；统一记忆位置需要另做迁移，不能顺手改路径导致“失忆”。

## 怎么验收

| 场景 | 预期 |
| --- | --- |
| 新建“陪伴 + 读文件”配置 | 无需新增 kind；可读工作区文件，不可调用未选择的写文件或 Shell 工具 |
| 选择一个不存在的工具或重复名称 | 加载前明确报错，原会话仍可用 |
| 按名称和路径加载同一配置 | 得到相同能力与状态目录 |
| 恢复旧 YAML 和已有 session | 名称、记录、原有工具限制保持兼容 |
| 加载 Skill 后请求未授权工具 | 执行层拒绝，不能因文档内容升级权限 |
| 切换预设 | 开新对话；旧对话可恢复，Plan 和临时验证状态不串到新预设 |

## 暂不做

不加入配置继承链、任意 Python 插件、插件市场、多用户权限系统或跨 Profile 自动共享记忆。先把单份配置的行为做清楚。

实施时先补旧配置兼容测试，再调整解析与组装，最后同步 README 和配置指南。未来规划完成后更新这里的状态，避免两份文档互相矛盾。
